- **本轮新增 P1**：详情页完整匹配理由、首页推荐免责提示、聊天内折叠理由、基于真实数据调整排序权重；埋点 P0、调权 P1。

## 一、结论摘要

项目现已更名为“Codeway”，定位为服务日常同路出行的“用户找用户结伴”平台；共同打车是 MVP 支持的重点场景，发单人跳转第三方平台完成叫车。本项目不做司机/车辆调度平台，这一边界保留。

当前最需要修改的不是继续增加功能，而是完成以下四件事：

1. **统一版本口径**：功能清单、页面、重点方案和竞品调研均已统一为Codeway v3.1 基线。
2. **把 MVP 收窄成可运行闭环**：手机号验证、发布、筛选、聊天、双向确认、第三方叫车跳转、车辆信息、订单共享、费用记录、评价、举报、手动 SOS 是一条完整闭环；推荐理由解释不参与 P0 排序加分。
3. **补齐状态、权限和异常规则**：目前大量验收标准只描述“能用”，没有规定谁能操作、何时锁定、失败后如何恢复。
4. **把页面设计从线框清单升级为流程设计**：补充空状态、权限拒绝、网络失败、订单争议、取消/补位、第三方 App 返回等关键状态，并让费用与安全信息在流程中可追溯。

## 三、功能文档修改建议

### 1. 先定义角色和行程状态机

在功能清单前增加“角色与状态”章节，避免后续页面和接口各自解释：

- 角色：普通用户、发单人、拼友、管理员、紧急联系人（外部接收者）。本项目不设司机端。
- 行程状态：`招募中 → 双向确认中 → 已成团 → 待叫车 → 已叫车 → 行程结束待结算 → 结算完成 → 待评价 → 已归档`。
- 例外状态：`用户取消`、`发单人取消`、`已满员`、`已过期`、`订单有争议`、`被管理员下架`。
- 明确状态变更权限：谁可以取消、谁可以上传车辆/订单、谁可以发起替代行程、什么时间点锁定费用比重。

### 2. 收紧 MVP 边界

建议把以下能力从“P0 必须”调整为 P1 或设置明确降级：

- **学生认证**：MVP 以手机号绑定为准，学生认证先做可选人工审核或邀请码；如果没有学校数据源，不要把“后台/规则核验”写成已确定能力。
- **短信 SOS**：微信订阅消息可作为首选，短信需要供应商、费用、模板和失败重试；P1 先保留“发送失败时展示 110/联系人电话”降级。
- **高德真实路径重叠**：放在 P1；MVP 用起终点距离和时间窗近似，并在 UI 标注“估算顺路”。
- **信用权益**：信用分、提前 14 天、免罚取消和每日限额依赖足够行为数据，P1 只做可解释的取消记录与成功率。
- **路线热度地图**：至少满足匿名聚合、最小样本数和时间延迟后再上线，避免暴露个人夜归路线。

### 3. 修正几个业务定义

- “手机号实名”建议改名为“手机号绑定/手机号验证”。手机号快捷授权不等于政府实名；如果确实需要实名，应单独定义实名服务、数据留存和失败处理。
- 费用模式只保留并定义三种：固定均摊、按人头固定金额、自定义比例。自定义比例必须校验总和 100%，并规定确认后是否允许修改。
- `是否拼车`与产品定位重复，建议从 B1 表单删除，改为“人数上限/是否接受新成员”。
- “车牌/车型必填”应改成车辆信息最小字段：车牌必填、车型和颜色选填；提供修改记录和全员可见时间。
- 订单截图和实际总车费需要校验：金额必须大于等于 0、截图格式/大小限制、重复提交覆盖规则、谁能发起争议、争议期间是否暂停评价。
- 取消规则需要区分“临期取消”和“实际爽约”。只有未到场且无合理原因才计为爽约；补位减免需要定义时间窗口和判定依据。

### 4. 处理第三方叫车的可行性风险

“自动带入出发地/目的地”不能直接作为所有平台都可用的 P0 验收标准。建议改成三层降级：

1. 若平台支持合法唤起和参数传递，使用唤起链接。
2. 不支持时，复制出发地、目的地和行程时间，并提供“打开第三方 App”按钮。
3. 用户返回后手动确认“已叫车”，再进入车辆信息录入。

同时补充：唤起失败、用户取消叫车、叫车平台不可用、发单人迟迟未录入车辆时，其他拼友看到什么状态和提醒。

### 5. 补充可验收的安全与隐私要求

- 未授权位置时，SOS 仍应发送行程基础信息和联系人电话，并明确“位置未获取”的原因。
- SOS payload 固定包含：触发人昵称/手机号后四位、行程 ID、起终点模糊信息、计划时间、当前 GPS（若获取成功）、触发时间和求助提示。
- SOS 长按、二次确认、冷却时间、重复触发、发送失败重试要分别验收；不要把“消息可达”写成平台可绝对保证的结果。
- 订单截图属于费用凭证，需明确保留期限、访问权限、删除/申诉流程；个人 GPS 只在手动 SOS 时采集并按文档销毁。
- 热力图和行程列表只展示模糊地点；建议热力图使用最小聚合样本数（如不少于 5 条）和延迟发布，具体阈值需在隐私评审后确认。

### 6. 增加产品验证指标

现有问卷通过标准可以保留，但还不足以判断产品是否成立。建议增加首轮试点指标：

| 指标 | 建议定义 | 用途 |
|---|---|---|
| 有效发布率 | 完成发布且未被系统拦截的行程数 / 发布尝试数 | 判断发布流程是否过重 |
| 成团率 | 双向确认成功行程数 / 有效行程数 | 验证“拼到人”核心价值 |
| 履约率 | 实际完成行程数 / 已成团行程数 | 验证取消与信誉机制 |
| 订单凭证提交率 | 已叫车且成功提交订单凭证的行程数 / 已叫车行程数 | 验证费用透明闭环 |
| 临期取消率 | 出发前 2 小时内取消数 / 已成团数 | 判断惩罚规则是否必要且公平 |
| 女性用户复用率 | 女性用户第二次使用人数 / 首次使用人数 | 验证夜间安全信任感 |
| 举报处理时效 | 从提交到首次人工处理的时间 | 验证治理闭环 |

## 四、竞品分析修改建议

### 1. 先修正竞品类型

当前 `04-竞品调研.md` 主要比较 GitHub/Gitee 开源项目，适合做“实现参考”，但不完全等于用户竞品。建议拆成三类：

1. **直接替代方案**：滴滴/高德等直接叫车、平台拼车功能；用户可能用它们解决“费用”和“到家”问题。
2. **同类产品**：校园拼车、夜间结伴、同路匹配产品；用于比较认证、匹配、取消、评价和安全。
3. **非产品替代方案**：班级群、宿舍群、社团群、线下固定拼车组；它们是低成本竞争者，应比较信任成本和触达效率。

现有 12 个开源项目可保留，但应在表头增加：来源链接、最后核验日期、证据类型（已实现/文档宣称/未发现），并把“没有某功能”改写为“在已查文档中未发现”，避免把检索结果当成绝对事实。

### 2. 调研结论建议改写

建议将“显著领先所有调研项目”改成更可证据化的表达：

> 在现有开源样本中，本项目对“用户对用户结伴、双向确认、第三方叫车衔接、订单凭证共享”进行了更完整的组合设计；但这些能力是否形成真实竞争优势，还需要和直接叫车平台、校园群组进行用户测试。

### 3. 增加竞品对照维度

现有矩阵应新增：

- 目标场景是否为夜间最后一段路；
- 是否支持用户对用户而非司机接单；
- 叫车、车辆确认、费用凭证之间的衔接；
- 取消/补位/申诉规则；
- 位置与隐私采集边界；
- 弱网、权限拒绝、第三方 App 不可用时的降级；
- 真实用户规模、活跃度或验证状态（未知时标“未知”）。

### 4. 把可学习点改成可落地任务

本轮继续保留“定价透明”任务，并新增“可解释推荐 + 决策可追溯”任务；用户关闭推荐理由入口明确不做。

- **定价透明（本轮采纳）**：把预估价格、分摊比例、实际订单金额、争议状态做成同一条费用记录。
- **可解释推荐（本轮采纳）**：MVP 仅返回时间相近、履约稳定、已验证、仍有空位四类理由码，最多展示 3 条，不参与排序加分；P1 再用真实曝光、点击、聊天、确认和履约数据调权。
- **决策可追溯（本轮采纳）**：P0 保存理由码、规则版本、行程 ID 和生成时间；P2 再做管理员查询界面。
- 严格准入、安全专项和多校扩展：本轮暂不处理。

## 五、页面设计修改建议

### P0 交互与流程

1. **首页 P02**：补充定位授权失败、无附近行程、日期无结果、网络失败、行程已满/已过期五种状态；增加推荐免责提示、理由最多 3 条和曝光/点击埋点；明确“附近”的服务区域或半径。
2. **发布 P04**：把表单拆成“路线/时间/人数/费用/拼友要求”五组；实时显示预计成团条件；自定义比例在输入时校验总和 100%。
3. **详情 P05**：在主按钮旁显示不可加入原因（已满、性别限制、未验证、时间冲突、已被拉黑）；P1 增加完整匹配理由说明；路径重叠 P0 不展示真实百分比。
4. **聊天 P06**：把费用比重、会合地点、双方确认做成可回看的结构化卡片，并记录确认时间；成团后显示锁定状态和费用变更申请；P1 将推荐理由放入折叠区。
5. **我的出行 P07**：建议 MVP 就拆“我发布的/我加入的”，因为取消权限、车辆录入权限和订单上传权限不同；每条行程显示明确状态机和下一步动作。
6. **叫车 P09/P10**：增加“正在等待发单人叫车”“叫车失败/改用其他平台”“车辆信息已更新”状态；车辆信息修改后通知全员。
7. **订单 P11/P12**：增加“查看原图、金额变更记录、提出异议、确认无异议”操作；订单有争议时在我的出行显示警告，并锁定结算、已付标记和互评；只有确认或争议超时后才生成最终分摊卡片。
8. **SOS P08**：作为全局安全入口，但不要用普通点击触发；长按进度、权限状态、发送中/成功/失败/冷却中都要可见。

### P1 视觉与信息架构

- 目前以 ASCII 线框为主，开发前应补一份视觉基线：颜色语义（安全/警告/已确认/争议）、字号层级、按钮状态、地图与卡片组件、微信小程序安全区和 375pt 下的溢出规则。
- 安全信息要“短而明确”：免责、位置采集、订单凭证保留分别放在触发前/上传前/设置页，不要在每页堆大段说明。
- 性别筛选和“仅女性”标识需要隐私说明，避免把未授权性别误显示为未知或默认值；在个人主页只展示用户明确同意展示的信息。
- P14 个人主页目前 P0，但“信用分”是 P1；P0 只展示次数、成功率和评价均值，信用分区域标记“即将上线”或移至 P1。
- P17 热力图必须有样本不足提示、时间范围和隐私说明；不显示可反推出单个用户的精确轨迹。

### 页面跳转图建议重画

当前跳转图把 P09→P10→P11→P12 画成线性流程，但真实情况存在分支。建议改为：

```text
已成团
  ├─ 发单人：第三方叫车 → 成功/失败/取消
  │                      └─ 成功 → 录入车辆 → 全员通知
  ├─ 任一成员：查看行程、聊天、手动取消
  └─ 行程结束 → 发单人提交订单
                    ├─ 成员确认 → 生成费用卡片 → 标记线下已付
                    └─ 成员异议 → 进入争议/人工处理
```

## 七、建议保留的产品原则

- 保留“拼友匹配，不做司机端”的定位。
- 保留双向确认和防误触，它们是信任机制的核心。
- 保留第三方叫车、车辆信息同步、订单截图共享，但给所有跨平台动作准备手动降级。
- 保留不做资金托管的边界，避免把产品变成支付平台。
- 保留手动 SOS 和低采集原则，不要在没有安全运营能力时承诺自动守护。
