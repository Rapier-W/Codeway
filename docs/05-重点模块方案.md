## 一、取消行程惩罚机制

### 1.1 MVP 基础版（P0，先落地）

**时间分段 + 月度计数**：

| 取消时机 | 后果 | 信誉影响 |
|---|---|---|
| 出发前 ≥24h 取消 | 无惩罚，仅记录"已取消" | 不计入成功率分母 |
| 出发前 24h ~ 2h 取消 | 通知对方；计一次"取消" | 不计成功；对方可见取消记录 |
| 出发前 <2h 取消 | 记一次“临期取消”；自动通知同乘人 + 推送替代行程 | 影响成功率；对方可评价 |

**附加规则（MVP）**：
- 实际爽约（约定时间未到场）单月 ≥3 次 → 信用降权 + 7 天禁止发布/加入
- 申诉通道：24h 内提交，管理员审核后撤销
- 取消后单子重新上架（有空位时）

### 1.2 P1 梯度惩罚方案（用户选定，更细腻）

**在 MVP 基础上增加"警告-扣分-限制-封禁"多级梯度，不做一刀切封禁**：

1. **时间分段**：同上（≥24h / 24h-2h / <2h）；临期取消与实际爽约分别留痕，只有实际未到场按爽约计入限制。
2. **角色差异化权重**：
   - 发单人 <2h 爽约：1 次计 **1.5 倍** 计数（权重 ×1.5，发起人责任更重）
   - 普通参与者 <2h 爽约：1 次计 1 次计数
3. **月度计分（非单纯计数）**：
   - 0 次：正常
   - 1 次爽约：弹窗警告，消息提醒"多次爽约将会被限制拼车能力"
   - 2 次爽约：功能限制——**7 天内只能加入行程，不能发布新行程**（未完全禁用）
   - ≥3 次爽约：7 天禁止发布 + 禁止加入，**信用分扣减**
4. **减免机制**：用户临期取消后，**若系统很快有新用户补上空位，本次爽约权重减半**（鼓励取消，不必硬撑去不了）
5. **申诉保留**：不可抗力（生病/急事）申诉，审核通过撤销记录

> 优点：梯度化不重罚失误；补位可减免；发起人加重更公平。
> 缺点：逻辑复杂；需判断"取消后空位是否被补上"（新增数据库逻辑，P1 实现）。

## 二、顺路匹配 · 路线重叠算法（高德 API）

### 2.1 方案选型

用户指定**调用高德地图 API** 计算真实路径重叠。方案分两期：

| 阶段 | 方案 | 说明 |
|---|---|---|
| MVP | 起终点邻近近似 | 不依赖 API，快跑通（排序用方案 A，顺路仅作标签） |
| P1 | **高德路线规划 API 真实重叠** | 精确计算，支撑三档顺路标签 |

### 2.2 P1 算法设计（高德 API）

**步骤**：
1. 后端调用高德**驾车路径规划 API**（`/v5/direction/driving` 或 `/v3/direction/driving`），输入两单各自的起终点坐标，各返回一条 `polyline`（"lng,lat;lng,lat;…"坐标串）
2. 将两条 polyline 分别**均匀采样**为 N 个点（如按 50m 间隔采样）
3. **重叠判定**：对单 A 的每个采样点，计算其到单 B 折线的**点-线段垂直距离**；距离 ≤ 阈值（**驾车 100m / 步行 50m**）判定为"重叠点"
4. **重合度** = 重叠采样点数 / 总采样点数（双向取均值，避免方向偏差）

```
重合度 = 0.5 × (A 落在 B 缓冲区的点比例 + B 落在 A 缓冲区的点比例)
```

**三档标签**（用户指定）：
- 重合度 60%+ → 「顺路」
- 重合度 80%+ → 「很顺路」
- 重合度 90%+ → 「几乎同路」

**技术要点**：
- 高德 Web 服务 API 是**后端调用**（需高德 Key，免费配额），与前端小程序地图 SDK（腾讯地图）互不冲突——后端算路线、前端画地图
- 点-线段距离计算用向量投影法（O(N×M) 可接受，路线点数 ~百级）
- 缓存优化：同一起终点对的路线结果缓存 24h，避免重复调用配额
- 高德 Key 需在服务端保管，**不得下发小程序端**

### 2.3 MVP 简化公式（不调 API 时）

```
重合度 ≈ w1 × 起点邻近度 + w2 × 终点邻近度 + w3 × 时间窗口重叠
起点邻近度 = 两出发地距离衰减（<1km 满分，1-3km 递减）
终点邻近度 = 两目的地距离衰减（同上）
时间窗口重叠 = 两时间窗口交集占比
默认权重：w1=0.35, w2=0.35, w3=0.30
```

## 三、行程列表推荐优先级（方案 A vs B 分析）

### 3.1 两个候选方案

**方案 A｜MVP 时间排序 + 理由码**（不加分、不调权）
```
主序列：出发时间升序（越近越靠前）
不使用认证、信用、顺路或空位加分项，不因理由码改变顺序。
后端为每张卡片计算最多 3 个理由码：
  TIME_CLOSE      时间相近：时间窗口有交集或计划时间差 ≤30 分钟
  RELIABLE        履约稳定：完成次数 ≥3 且成功率 ≥80%
  VERIFIED        已验证：完成学生认证（手机号验证不作为展示理由）
  OPEN_SLOT       仍有空位：当前仍可加入（MVP 单车总人数为 3 或 4，示例 1/3 或 2/4）
低信用发布者可以出现在列表中，但不展示正向推荐理由文案。
```

**方案 B｜P1 综合得分排序**（时间+匹配度混合）
```
Score = 时间衰减分(0-40) + 顺路重合得分(0-30) + 信誉分(0-20) + 空位分(0-10)
时间衰减：越临近出发分越高，>48h 快速下降
顺路重合：90% 拿满 30 分，60% 拿 15 分，<60% 得 0
信誉分：成功率/爽约计算，学生认证额外加成
空位分：空位越多分越高
保护：已过出发时间的行程直接过滤
```

### 3.2 对比分析

| 维度 | 方案 A（时间主序） | 方案 B（综合得分） |
|---|---|---|
| 用户直觉 | ✅ 强：时间轴不乱，符合"我今晚几点走"心智 | ❌ 弱：时间可被其他分超越，出现"明天 23 点排到今天 22 点前" |
| 场景匹配 | ✅ 夜归场景时间窗窄（21:00-24:00），时间是第一约束 | ⚠️ 综合分模糊了时间的硬约束 |
| 成团效率 | ⚠️ 顺路高匹配提升有限 | ✅ 高顺路高信誉整体靠前，理论提升成团概率 |
| 开发/调参 | ✅ 简单，规则直白 | ❌ 权重调试成本高，MVP 无数据支撑 |
| 演进性 | ✅ 可平滑升级（段内换成综合分） | ⚠️ 需用户适应，调整成本高 |

### 3.3 推荐结论：**MVP 采用方案 A，P1 演进为“时间窗硬排序 + 窗内数据调权”**

**理由**：
1. **同路场景决定时间必须是硬排序**：无论通勤、活动散场还是夜间返程，用户的核心心智都是“我在某个时间窗口出发，找同一时段的单”。日期已由导航栏分页（7 天），同一天内若时间被信誉/顺路打乱，用户找单效率反而下降——方案 B 的“时间衰减分”本质也想让时间主导，但混入可交换分数后必然出现反直觉排序。
2. **推荐理由与排序解耦**：用户能看到匹配依据，但理由码不改变列表顺序，避免推荐文案被误解为信用担保或系统加权结果。
3. **P0 先积累数据**：MVP 阶段只记录曝光、点击、聊天、确认、取消和完成，不根据少量样本拍权重。
4. **演进路径清晰**：P1 在同一时间窗内使用真实数据调节路线、履约、认证和空位权重；高德路线标签上线后再增加路线理由。

**P1 混合公式（演进目标）**：
```
排序 = 先按出发时间分窗（如每 30 分钟一窗，窗内时间升序）
       窗内排序 = 综合分（顺路 0-30 + 信誉 0-20 + 空位 0-10，时间已由窗序保证）
```

**落地要点（MVP 方案 A 实现）**：
- 数据层：SQL 查询按 `depart_time ASC` 排序
- 过滤保护：`depart_time > now` 硬过滤，已出发单不展示
- 后端返回 `reason_codes[]`，按固定优先级去重后最多保留 3 条；低信用发布者返回空理由数组
- 记录曝光、卡片点击、推荐理由展示、发起聊天、双向确认、取消和完成事件；事件包含规则版本，支持去重
- 不提供用户关闭推荐理由入口；P2 仅增加管理员查询界面

## 四、三个模块的依赖关系

```
列表排序（方案 A）── 输出 ──► 推荐理由码（MVP 时间/履约/认证/空位）
      │
      ▼
取消惩罚（MVP 基础版）── 提供 ──► 信誉分/成功率 ──► 履约稳定理由码
      │
      ▼ P1
梯度惩罚（月度计分）── 产出 ──► 信用分 ──► P1 时间窗内调权
```
